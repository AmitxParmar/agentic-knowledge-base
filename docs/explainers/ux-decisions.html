The UX contract the whole stack obeys

One line from docs/ux.md defines the client experience: the user sees what the system is doing, never how the model is thinking. Two artifacts enforce it — a frozen vocabulary of progress stages, and a hard requirement that every cited claim stays clickable back to its source chunk.

The core principle

What's on the channel, and what never is

Progress stages are the only window into an in-progress run. The frontend never renders a bare spinner for the thinking phase, and never streams raw model output mid-run.

Allowed on the client

  • Stage names, verbatim from the vocabulary below
  • The final answer text, once ready
  • Citations — numbered references the user can click through to the source passage
  • User-visible error messages in plain English

Explicitly forbidden

  • Raw chain-of-thought or scratchpad reasoning
  • Hidden system / agent prompts
  • Internal tool-call payloads — retrieval queries, rerank scores
  • Any free-form status strings invented mid-stream

Why so strict? Retrieval failing or a model looping is not the user's debugging session. The vocabulary surfaces just enough to feel transparent — "it's searching, now it's drafting" — while the internals stay free to change without breaking the UI. The same rule is duplicated in the agent-facing contract: conventions.md → Progress-event pattern.

Frozen vocabulary — docs/ux.md

Progress stages

These exact strings are the only text allowed on the progress channel. Add a word and it fails review; add a stage and you update ux.md first, then the code. In the browser they render as an inline strip below the answer area, with the current stage pulsing until the answer lands.

Trust mechanism

Every claim carries a receipt

The citation display requirement is a success criterion, not a nicety: an answer with no visible citations has failed docs/specs/researcher.md → Success Criteria, no matter how good the prose reads. Two patterns make it hold up under change:

1 · Citation-at-retrieval

A citation record is created the moment a chunk is retrieved, attached to the evidence itself — never reverse-engineered from the final answer text after the fact.

Downstream stages pass the reference along untouched, so the link can't quietly fall off mid-pipeline.

↳ enforced as a rule in the root AGENTS.md + conventions.md

2 · Transport keeps citation + answer separate

Citations travel as their own structured event (kind: "citations" on the AG-UI SSE stream), carrying chunk_id, source_ref, and relevance_score.

The UI resolves [1] [2] markers in the answer against that list — grouping by document, showing the source and score on hover.

Why it looks the way it does

UX decisions and their rationale

Stage strip, not a chat-of-thought

The V1 design imagined "watch the reasoning unfold" multi-agent trace views. The MVP rejected that: reasoning views leak implementation, and the agents they assume (Planner, Critic) don't exist yet.

↳ deferred to Phase 2, per ux.md Out of Scope

Terminal UI aesthetic

The conversation surface reads like a research terminal — < QUERY > / << ANSWER >> headers, an indexed thread rail, and a >>> RUN composer. It matches the product's evidence-first stance: dense information, no decorative chrome.

↳ apps/web · research-chat.tsx

Chat surface, SSE transport

The UI is a conversation thread (TanStack AI useChat), but the wire is a one-way POST + SSE stream. Server Sent Events give browser-native resume, and — unlike a WebSocket — a plain HTTP request carries the question, so history, auth headers, and error handling reuse normal fetch machinery.

↳ ADR-005 · see explainer 03

Who is this for

Persona: an analyst or engineer who already trusts nothing they read and wants every claim checkable. Anti-persona for MVP: a team platform with roles, sharing, and audit trails (RBAC is a Phase 2 goal).
