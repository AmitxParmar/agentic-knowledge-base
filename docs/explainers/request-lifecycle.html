From keystroke to cited answer — the wire

The whole app speaks one protocol: a single POST, and then a one-way Server-Sent Events stream of AG-UI events. This page follows a question from the browser through the Research Agent and back — including the CUSTOM events that carry stage labels and citations without ever touching the answer text.

The happy path — POST /api/research/chat

One question, down and back

TanStack AI's fetchServerSentEvents connection adapter sends the question as a normal POST and then subscribes to the response body as SSE. The server emits typed AG-UI events the client folds into chat state — no hand-rolled WebSocket, no reconnect logic.

The split is deliberate: stages and citations are CUSTOM events ({"type":"CUSTOM","name":"stage","value":{...}}), while the answer is a standard TEXT_MESSAGE_CONTENT event. The client SDK routes custom events to its onCustomEvent(name, value) callback, so the progress strip and the citation rail stay structurally separate from the chat transcript.

What actually crosses the wire

The SSE stream, verbatim

One event per data: frame. The frontend parses each as JSON and dispatches on type. This is the happy path for a successful run. 

// request
POST /api/research/chat
{ "question": "What does report.pdf say about revenue?", "threadId": "…" }

// stream
data: {"type": "RUN_STARTED", "threadId": "…", "runId": "…"}

data: {"type": "TEXT_MESSAGE_START", "messageId": "…", "role": "assistant"}

data: {"type": "CUSTOM", "name": "stage", "value": {"stage": "Searching documents..."}}
data: {"type": "CUSTOM", "name": "stage", "value": {"stage": "Reviewing evidence..."}}
data: {"type": "CUSTOM", "name": "stage", "value": {"stage": "Generating report..."}}
data: {"type": "CUSTOM", "name": "stage", "value": {"stage": "Finalizing answer..."}}

data: {"type": "CUSTOM", "name": "citations", "value": {"run_id": "…", "citations": [
        {"chunk_id": "…", "source_ref": "report.pdf, chunk 3", "relevance_score": 0.91},

Failure is user-facing too

Structured error codes

When a run fails, the client gets a RUN_ERROR event with a stable machine code and a plain-English message — never a stack trace. The selector lives in apps/api/src/research/router.py and maps exception types to codes.

CodeTriggerUser sees
RATE_LIMITProvider 429 (Groq/OpenRouter)"The model provider is rate limited. Please wait a moment and try again."
PROVIDER_ERRORProvider down / unreachable"The model provider is unavailable. Please check provider status and try again."
RETRIEVAL_ERRORHybrid search / embedding failure"An error occurred while searching the documents. Please try again."
TOOL_PARSE_ERRORMalformed model tool call"The model produced a malformed tool call. Please try again."
AGENT_ERRORCatch-all"An error occurred during the research run."
The other loop — POST /api/ingestion/upload

Ingestion handshake

Uploads are deliberately async: the request returns immediately with a job id, and an arq worker does the heavy lifting through the same stage vocabulary ("Uploading… Extracting… Chunking… Creating embeddings…"). The client polls the job and shows those stage names — the same UI language as a research run.

StepProducerResult
1 · uploadFastAPI routedocuments + queued ingestion_jobs row, raw file to storage (R2/disk). Returns 202-style job id.
2 · extractarq workerDocling (PDF) · faster-whisper (audio) · tree-sitter+gitingest (repo) → structured text.
3 · chunkarq workerChonkie — semantic boundaries, not fixed token counts.
4–5 · embedarq workerBGE-M3 vector per chunk; metadata extracted alongside.
6 · persistarq workerChunk rows → Postgres · vectors → in-process Turbovec (rebuilt from PG at boot).

One vocabulary, two surfaces. Both ingestion and research reuse the frozen stage strings from docs/ux.md — the user always sees the same style of progress whether they're waiting on a PDF to become searchable or on an answer to arrive.
